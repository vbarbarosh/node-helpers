# Project audit — 2026-11-09

## Executive summary

This audit reviewed the package surface, every helper under `src/`, the tests,
the browser bundle, the documentation generator and the published docs page,
the npm package contents, CI, and the release workflow at commit `6296b4f`
(v3.79.2) using Node.js `v24.20.0` and npm `11.19.0`. It is the third audit,
after `notes/audit-2026-07-28.md` (commit `da24f51`) and
`notes/audit-2026-09-02.md` (commit `c471fff`, v3.78.0). It first re-checks
each of the 60 earlier findings and then reports 33 new ones (AUD-61 to
AUD-93).

Every command below was run in a `git archive` copy of `HEAD`. No Redis was
available this time, so the 18 Redis compatibility tests skipped.

- `npm test`: 1,394 passing, 19 pending (the 18 Redis tests and the
  intentionally skipped "survived SIGKILL" case). Two of eight further runs
  failed in the watchdog tests while the machine was busy (AUD-91).
- `npm run lint`: passing.
- `npm run check:cdn`: passing (Axios 1.20.0 in manifest, lock, template,
  dist, and docs), although the docs page runs another version (AUD-63).
- `npm run coverage`: passing at 79.56% statements/lines, 87.41% branches,
  79.02% functions (up from 73.90% / 87.54% / 77.60%).
- A same-context webpack build produced a byte-identical `dist/browser.js`,
  `dist/index.html` and `docs/js/browser.js`.
- `bin/build-docs.js` and `bin/update-version.js` produced no diff against the
  committed `docs/` and `README.md`.
- `npm pack --dry-run --json`: successful, 507 package entries, approximately
  333 KB unpacked; only `LICENSE`, `README.md`, `package.json`, `dist/*` and
  `src/**/*.{js,md}` without tests or `.d/` fixtures. The published 3.79.2
  has the same count and size and carries a provenance attestation.
- `npm audit --omit=dev`: 1 high advisory in the production lock (AUD-92);
  it was clean in July and September.
- `npm audit` (full): 14 vulnerabilities (3 high, 10 moderate, 1 low), up
  from 8.
- Both workflows were green for `6296b4f` and the `v3.79.2` tag.

Since the previous audit, eleven of its open findings were remediated with
tests: the AES helper (AUD-03, the first to close of the five High findings
that were open in September) and ten of the September findings (AUD-21 to 27
and AUD-32 to 34). Two more are partly fixed (AUD-05, AUD-15). Of the 60
findings, 17 are now remediated, 5 partly, and 38 open. Three July **High**
findings are unchanged and were reproduced again today: Redis TLS verification
(AUD-01), SFTP host keys (AUD-02) and the unauthenticated watchdog heartbeat
(AUD-07). Secrets still pass the error-report mask in several shapes (AUD-05),
and the Axios gate that closed AUD-04 does not see the version the docs page
runs.

The new findings contain one **High** item: `http_stream_range` never
settles and leaks a file descriptor when a client disconnects right after
sending its request, so a few hundred such requests exhaust the server's
descriptors (AUD-61). The most significant of the 20 new Medium findings
are: data encrypted before v3.78.1 can no longer be decrypted, a side effect
of the AUD-03 fix shipped in a patch release (AUD-62); `fs_rmrf` deletes
files outside its tree when a symlink stands where it expects a directory
(AUD-64); one vanished or unreadable entry fails a whole directory listing
(AUD-66); `stream_lines` and `sanitize_var_name` take quadratic time on
ordinary input (AUD-68, AUD-69); the range client lets Axios decompress
ranged responses (AUD-70); `http_put_file` can send a second request's worth
of bytes after its declared body (AUD-72); a dropped Redis connection kills
the process (AUD-74); and sorting by a key that one record lacks leaves the
array unsorted (AUD-78).

Three of the September fixes introduced problems of their own: AUD-62 above,
`urlparts` losing the credentials of non-http URLs (AUD-82), and five smaller
behaviour changes (AUD-83). The package has no changelog, so none of these
reached consumers as a notice (AUD-93).

Severity meanings are the same as in the previous audits:

- **High:** plausible compromise, credential disclosure, corrupted security
  guarantees, or sustained service unavailability.
- **Medium:** material incorrect behavior, data loss, hangs, hidden failures, or
  a significant defense/testing gap.
- **Low:** localized correctness, maintenance, deployment, or developer
  experience issue with limited immediate impact.

Every new finding was reproduced at `6296b4f` with a standalone script and
re-run a second time before it was written down; what could only be
established by reading is marked so. The last section lists what this audit
did not exercise.

### What remains of AUD-05

`c6cdebf` masks the cases the July audit named, and a report for a request
without secrets is unchanged. The doc now says the REQUEST section is masked
"so the report can be logged or sent to error tracking"; these still reach
the report in clear text:

- **Headers.** The mask is a list of seven exact names
  (`src/format_error_report.js:6-14`, `:117`). Of 17 common credential
  headers, 15 pass: `X-Goog-Api-Key`, `Private-Token`, `X-Access-Token`,
  `X-Amz-Security-Token`, `X-CSRF-Token`, `X-XSRF-TOKEN`, `apikey`,
  `CF-Access-Client-Secret`, `X-Vault-Token`, `Ocp-Apim-Subscription-Key`,
  `DD-API-KEY`, `X-Auth-Key`, `X-Shopify-Access-Token`, `X-Session-Token`,
  `Token`. The same 17 names used as query parameters are all masked: the
  two masks disagree.
- **Userinfo.** The regex stops at the first `@` and needs a scheme
  (`:138`): `https://admin:P@ss_SECRET@host/x` is reported as
  `https://***@ss_SECRET@host/x`, and `//admin:SECRET@host/x` unchanged.
- **Query names.** Names match on a separator or camelCase boundary against
  13 words (`:139`, `:153-160`). None of 29 tried names was masked, among
  them `authtoken`, `clientsecret`, `refreshtoken`, `sessionid`, `jwt`,
  `code`, `sid`, `otp`, `passphrase`, `SAMLResponse`.
- **Structure.** `;`-separated pairs, the first parameter of a fragment
  (`#access_token=`), a URL nested in a parameter value, plain or
  percent-encoded, and JSON in a parameter value.
- **Outside the REQUEST section.** `error.message` and `error.stack` are
  printed as they are (a Node `fetch()` URL-parse error carries the whole
  URL, credentials included), header values that hold a URL (`Referer`) are
  not passed through the URL mask, and the first 10,240 characters of the
  response body are copied (`:73`).

```sh
node -e "const f=require('./src/format_error_report');
const e=Object.assign(new Error('x'),{config:{method:'get',url:'https://admin:P@ss_SECRET@db.example/x#access_token=FRAG_SECRET',headers:{'X-Goog-Api-Key':'GOOG_SECRET',Authorization:'Bearer AUTH_SECRET'}}});
console.log(f(e).match(/\w+_SECRET/g))"
```

Observed: `[ 'ss_SECRET', 'FRAG_SECRET', 'GOOG_SECRET' ]`.

To close it: decide header sensitivity with the same segment rule as query
names and extend the word list (`session`, `sid`, `jwt`, `csrf`, `xsrf`,
`code`, `passphrase`, `assertion`), matching the words also as prefix or
suffix of unseparated names; mask userinfo up to the last `@` of the
authority, scheme-relative URLs included; run the URL mask over fragments,
`;` pairs, decoded values, header values, `message` and `stack`; add a
caller hook for secrets carried in the path.

## New findings

### AUD-61 — `http_stream_range` never settles and leaks its file descriptor when the client disconnects early

**Severity and impact:** High — availability. A client that sends a GET
and closes the socket within about a millisecond strands the handler for
good and leaks one file descriptor for the life of the process. A few
hundred such requests, as many as `ulimit -n` allows, leave the server
answering 500 `EMFILE` to everyone until it is restarted. No authentication
or special request is needed, and an ordinary client that aborts a request it
has just sent does the same.

**Description:** The handler awaits `fs_size` and `fs_fopen` before it
registers `req.once('close')`. When the connection is already gone, that
listener never fires, `res.write()` on the destroyed response returns
`false`, and the handler waits for a `drain` or `close` on `res` that was
emitted before it started listening. The `finally` with `fs_fclose` is never
reached, and the descriptor is a plain number, so nothing reclaims it.
Nothing checks `res.destroyed` or `req.destroyed`. A route that awaits
anything before calling the helper widens the window by that much.

**Relevant locations:**

- `src/http_stream_range.js:73` (descriptor opened).
- `src/http_stream_range.js:77-78` (listener registered after two awaits).
- `src/http_stream_range.js:88`, `:96-115` (waits after `write()` returned
  `false`), `:121-123` (`finally` never reached).
- `src/http_stream_range.test.js` (no client-disconnect case).

**Verification steps:**

1. Serve a file with the route from `http_stream_range.md`:
   `app.get('/file', (req, res) => http_stream_range(req, res, file))`.
2. 200 times, open a socket and run
   `s.write('GET /file HTTP/1.1\r\nHost: x\r\n\r\n', () => s.destroy())`.
3. Three seconds later count the pending handlers and the entries of
   `/proc/self/fd`.
4. Repeat against a server started under `ulimit -n 150` and send one
   honest request afterwards.

The audit observed `handlers {"pending":200,"settled":1}`, open descriptors
`23 -> 223`, and under the limit `HTTP/1.1 500 Internal Server Error` for
the honest request, with `EMFILE: too many open files` in the server log.
With the client closing 0 ms after the request 200 of 200 handlers were
stranded, at 1 ms 167, at 3 ms 11, at 10 ms none.

**Expected behavior:** The handler settles and closes the file whenever
the request or the response is gone.

**Actual behavior:** It stays pending with the descriptor open; descriptor
exhaustion then fails every request.

**Recommended remediation:**

1. Treat a dead connection as a stop condition: check
   `res.destroyed || req.destroyed` before the loop, in the loop condition,
   and before waiting for `drain`.
2. Or replace the loop with `stream.promises.pipeline(fs.createReadStream(
   file, {start: first, end: last}), res)`, keeping the short-read check.
3. Add a test: 100 requests destroyed right after being written, then
   assert that every handler settled and the descriptor count is back.

### AUD-62 — `crypto_decrypt_aes256` can no longer read anything encrypted by v3.78.0 and earlier

**Severity and impact:** Medium — data access. Data encrypted with any
release up to v3.78.0 becomes unreadable after an in-range upgrade (`^3`),
because the new format shipped in a patch release, v3.78.1. Nothing is
destroyed, but the caller has to downgrade or re-implement the old cipher to
get the data back, and finds out only when a decrypt throws.

**Description:** `98f9673` (the AUD-03 fix) replaced the
`[0x10][16-byte IV][AES-256-CTR ciphertext]` envelope with a version 1 GCM
envelope and made the helper throw `malformed envelope` for any first byte
other than `0x01`. The July recommendation to ship a migration path with the
new format was not done: there is no legacy reader, and neither `.md` file
mentions older data. An old envelope always starts with `0x10`, so the two
formats can be told apart safely.

**Relevant locations:**

- `src/crypto_decrypt_aes256.js:24-26`.
- `src/crypto_decrypt_aes256.md`, `src/crypto_encrypt_aes256.md`.

**Verification steps:** Decrypt the fixed vector the test suite used until
v3.78.0 (`hello` under `pass123`):

```sh
node -e "const d=require('./src/crypto_decrypt_aes256');
try { console.log(d('pass123', Buffer.from('10000102030405060708090a0b0c0d0e0f27897103cc','hex')).toString()) }
catch (e) { console.log('throws:', e.message) }"
```

Observed: `throws: crypto_decrypt_aes256: malformed envelope`. At `c471fff`
the same call returned `hello`.

**Expected behavior:** Old data stays readable through an explicit legacy
path, and the format change is announced.

**Actual behavior:** Every old envelope throws, with no helper and no
documentation for recovery.

**Recommended remediation:**

1. Add a migration-only reader (`crypto_decrypt_aes256_legacy`, or an
   explicit `{legacy: true}`) for envelopes whose first byte is `0x10`; keep
   the default path rejecting them, since the old format is unauthenticated.
2. Describe the change and a decrypt-old, encrypt-new procedure in both
   `.md` files and in the release notes.
3. Keep the fixed v3.78.0 vector as a test of the legacy reader.

### AUD-63 — The docs page runs Axios 1.11.0, not the 1.20.0 that `check:cdn` verifies

**Severity and impact:** Medium — security gate and supply chain. AUD-04 was
closed by a gate that compares the Axios version in each shipped page with
`package.json`. The published docs page passes that gate and still ends up
with `window.axios` at 1.11.0, a release with 32 published advisories (12
high), because a second script loads its own copy afterwards. The `http_*`
helpers of the bundle on that page use the older copy. The page only fetches
its own `data.json`, so the practical exposure is small; the defect is that the
gate reports a version the browser does not run.

**Description:** `docs/index.html` loads `axios@1.20.0`, then
`@vbarbarosh/ui-helpers@0.4.0/src/static/js/bundle.js`. That bundle writes
its own list of scripts into the page, `axios@1.11.0` among them, and the
later script replaces the global. `bin/check-cdn-dependencies.js` reads the
HTML source only and requires exactly one versioned Axios tag in it, so it
cannot see what the bundle adds.

**Relevant locations:**

- `docs/index.html:16-17`.
- `bin/check-cdn-dependencies.js:32-38`.
- `@vbarbarosh/ui-helpers@0.4.0`, `src/static/js/bundle.js:22` (outside this
  repository).

**Verification steps:** Open the published page in a headless browser, wait
for it to render, and read `axios.VERSION` and the Axios script tags in the
document:

```js
await page.goto('https://vbarbarosh.github.io/node-helpers/', {waitUntil: 'networkidle'});
await page.evaluate(() => [axios.VERSION, [...document.scripts].map(s => s.src).filter(s => s.includes('/axios@'))]);
```

The audit observed `1.11.0` and two tags, `axios@1.20.0/dist/axios.min.js`
followed by `axios@1.11.0/dist/axios.min.js`. The npm advisory endpoint
(`/-/npm/v1/security/advisories/bulk`) lists 32 advisories for `axios@1.11.0`
and none for `1.20.0`. `npm run check:cdn` passes.

**Expected behavior:** The page runs the Axios version the gate checked.

**Actual behavior:** The gate checks 1.20.0; the page runs 1.11.0.

**Recommended remediation:**

1. Move to a `ui-helpers` release that does not load its own Axios, or load
   the page's pinned Axios after the `ui-helpers` bundle.
2. Check the effective version: a headless-browser test that opens
   `docs/index.html` and asserts `axios.VERSION` equals
   `package.json` `dependencies.axios`.
3. Keep the source check as a fast first gate.

### AUD-64 — `fs_rmrf` deletes files outside the tree when a symlink stands where it expects a directory

**Severity and impact:** Medium — data loss, security boundary. Files in a
directory that was never named are deleted, although `src/fs_rmrf.md:3`
promises that "a symlink is removed itself — its target is never followed".
The library is exposed itself: the Redis spawn worker starts the `fs_tempdir`
cleanup when the direct child exits, while the job's descendants may still be
writing into that directory.

**Description:** `fs_rmrf` decides "directory" with `lstat(path)`, then
calls `readdir(path)` and builds the children with `path.join(path, name)`.
Whatever `path` is at that later moment is followed. Three cases:

- A race: the directory is replaced by a symlink between the `lstat` and the
  `readdir`. All children start at once (AUD-14), so a subdirectory's
  `readdir` waits behind its siblings and the window is wide.
- A trailing slash: `lstat('link/')` follows the link, so the target's
  contents are removed and only the final `rmdir` fails. (`rm -rf link/`
  does the same; `fs.promises.rm` leaves both the link and the target.)
- `link/../x`: the kernel resolves the root through the link, `path.join`
  resolves the children textually, so entries are deleted from a different
  directory than the one that was read.

**Relevant locations:**

- `src/fs_rmrf.js:14` (`lstat`), `:20-21` (`readdir` follows; children by
  `fs_path_join`), `:23`.
- `src/fs_rmrf.md:3`.
- `src/fs_tempdir.js:43`, called from
  `src/redis_poll_zshift_spawn_rpush.js:137`.

**Verification steps:** The trailing slash:

```sh

node -e "require('./src/fs_rmrf')(process.argv[1]).catch(e => console.log(e.code))" "$d/link/"
ls -A $d/precious | wc -l
```

Observed: `ENOTDIR`, then `0`. The race, with two real processes and no
stubs: a tree of 20,000 files and 50 subdirectories; a second process
watches the tree and, on the first event, renames one subdirectory away and
puts a symlink to a directory outside the tree in its place. The audit
observed the three files outside the tree deleted in 5 of 5 rounds, and none
in the control where the links were there from the start.

**Expected behavior:** Only entries inside the directory identified by the
first `lstat` are removed; a symlink is unlinked, never descended into.

**Actual behavior:** The contents of the link's target, or of a textually
different directory, are deleted, and the call then rejects.

**Recommended remediation:**

1. Normalise once at entry (`path.resolve(path)`, which also drops the
   trailing separator) and use that one string for the `lstat`, the
   `readdir` and the joins. This closes the second and third cases.
2. For the race, `lstat` the directory again after `readdir` and compare
   `dev` and `ino` with the first result before touching a child. Node has
   no `openat`, so this narrows the window without closing it; say so in
   `fs_rmrf.md`.
3. Refuse an empty or non-string path, `/`, and a path whose last segment
   is `.` or `..`, as `rm` does (today `''` and `undefined` resolve
   silently, and `.` empties the working directory before its `rmdir`
   fails; by reading only).
4. Add a trailing-slash test and a swap test with a stubbed `lstat`.

### AUD-77 — `countdown` delivers `Timeout` up to `tick_ms` late in about one call in five

**Severity and impact:** Medium — wrong timing. A 100 ms timeout

**Expected behavior:** `Timeout` within a few milliseconds of `timeout`.

**Actual behavior:** On time, or at the next `tick_ms` boundary.

### AUD-83 — Side effects of the September fixes

**Severity and impact:** Low — compatibility and correctness. Each case
is a behaviour change or a gap introduced by a commit that closed an earlier
finding, and each shipped in a patch release.

- **The AES helpers block the event loop for tens of milliseconds per
  call.** `src/crypto_encrypt_aes256.js:24`, `src/crypto_decrypt_aes256.js:40`
  call `crypto.scryptSync` on every call. Observed: 0.03 ms per call at
  `c471fff`, 30 to 48 ms at HEAD; 20 decrypts in a row held the event loop
  for 569 ms. There is no asynchronous variant, no way to reuse a derived
  key, and the docs do not mention the cost.
- **The pid helpers throw for a numeric string.** `src/pid_exists.js:6-8`,
  `src/pgid_exists.js:7-9`, `src/pid_kill_grace.js:11-13`,
  `src/pgid_kill_grace.js:12-14` use `Number.isInteger`. A pid read from a
  pid file or an environment variable worked through v3.78.0
  (`process.kill` accepts it) and now gives
  `TypeError: pid_exists: invalid pid: 25978`; `pid_kill_grace("25978")`
  rejects and the process keeps running. The change is tested and
  documented; the message does not quote the value, so the string looks
  valid.
- **`escape_content_disposition` turns every character above U+00FF into
  `?`.** `src/escape_content_disposition.js:17`. `"файл.txt"` gave
  `"файл.txt"` at `c471fff` and gives `"????.txt"` now. Node's `setHeader`
  refused the old output, but callers that put the value elsewhere (a
  presigned `response-content-disposition`, a hand-built multipart header)

`toWellFormed()` before `encodeURIComponent`; convert the result to a string
in `shell_lines` or reject `encoding: 'buffer'` with a clear message.

### AUD-85 — HTTP, download and URL helper edge cases

**Severity and impact:** Low — localized correctness, wasted work and
doc mismatches.

- **`fastdl` restarts every in-flight chunk after a fatal error.**
  `src/fastdl.js:82-86`, `:104`. The `catch` destroys the active streams to
  abort, but each writer is `run().catch(run).catch(run)`, so the destroy

  Retries are immediate and also apply to errors that cannot succeed.
- **An empty resource cannot be read.** `src/http_get_stream_range.js:20-23`
  synthesizes `bytes 0--1/0` for a 200 with `Content-Length: 0` and rejects
  with `Invalid Content-Range`; `fastdl` rejects with the server's 416
  (`src/fastdl.js:54`).
- **`http_stream_range` sends `Content-Disposition` on HEAD only**
  (`src/http_stream_range.js:30-38` against `:81-86`). The GET response,
  the one a browser uses to name the saved file, has none. The doc
  describes it, so it is a design gap.
- **`http_get_blob` in Node resolves with a lossy string**, not a `Blob`
  and not an error (`src/http_get_blob.js:5`): 12 bytes sent came back as a
  string of 20 bytes.
- **`urlmod` and `urlclean` rewrite parameters they were not asked to
  touch.** Both round-trip the whole query through a decoder
  (`src/urlmod.js:22`, `:42`; `src/urlclean.js:18-22`), so a

**Recommended remediation:** Set an `aborted` flag before destroying the
streams and make `run()` rethrow when it is set; do not retry

in Node. Edit the raw query text field by field in `urlmod` and `urlclean`.

### AUD-88 — Timing and supervision helper edge cases, second batch

**Severity and impact:** Low — deadlines that never arrive or arrive at
the wrong time, and failures that are reported as success. None repeats a
case of AUD-58.

- **A duration passed as a string disables the deadline.**
  `src/HeartbeatServer.js:27-29`, `src/countdown.js:17`,
  `src/pid_kill_grace.js:7`, `src/pgid_kill_grace.js:8` compute
  `Date.now() + '300'`, a string and a deadline centuries away, while the
  timers coerce the same string, so everything looks alive.
  `new HeartbeatServer('300')` with no pings and
  `countdown({timeout: '300'})` were still pending after 3 s;
  `pid_kill_grace(child, {grace_timeout_ms: '300'})` never sent `SIGKILL`
  to a child ignoring `SIGTERM` ("grace time remaining:
  1,792,459,708,501,924ms"). A value from an environment variable or a
  flag arrives this way.
- **Deadlines follow the wall clock.** The same four helpers measure with
  `Date.now()` while their timers run on the monotonic clock. With the
  clock stepped (simulated by shifting `Date.now()`): back 3 s,
  `HeartbeatServer(300)` with no pings fired after 3,307 ms; forward 1 h, it
  declared a worker pinging every 150 ms dead, and
  `pid_kill_grace(grace_timeout_ms: 5000)` sent `SIGKILL` after 110 ms to a
  child that needed 600 ms to stop cleanly.
- **`cli` exits 0 when `report` throws** (`src/cli.js:19-28`). `reject()`
  calls `report(error)` and then `process.exit(code)`; a throw in between
  ends the process naturally with code 0. A `main` that rejects with `null`
  under a reporter reading `error.message`, as the watchdog's does
  (`src/cli-apps/watchdog.js:37-40`), exits 0; so does an
  `ExitCodeError(124)` under a reporter that fails while formatting.
- **A failing callback escapes `parallel` and `countdown`.** In
  `src/parallel.js:62-66` the final `tick()` runs before
  `clearInterval` and `resolve()`: one throw from a progress renderer
  leaves the promise pending and the interval throwing an uncaught
  exception every second. `src/countdown.js:53-62` wraps `ctx.tick` in
  `try/catch`, which misses an async tick that rejects, although
  `countdown.md:10` says it rejects and stops the timers.
- **`make_progress.add()` scans its whole 10-second history on every
  call** (`src/make_progress.js:28`, `:33`), and `fastdl` calls it once per
  chunk (`src/fastdl.js:126`). With 16 KiB chunks from a local source,
  1 GiB took 18.9 s (54 MiB/s) with 95% of the time inside `add()`, against
  0.4 s with `add()` replaced by a counter. It matters only above a few
  hundred megabits per second.

**Recommended remediation:** Validate durations with
`assert_positive_integer`; measure intervals with `performance.now()`; wrap
`report(error)` in `try/catch` and always reach `process.exit`; call
`fail(error)` when `tick()` throws in `parallel`, and use
`Promise.try(() => ctx.tick(ctx)).catch(ctx.reject)` in `countdown`;
coalesce samples younger than about 250 ms and evict from the front in
`make_progress`.

### AUD-89 — Small cases in `logger`, `AbortError`, the pollers, `mongo_stream_upsert`, `shell` and the watchdog

**Severity and impact:** Low — hidden errors in logs, misclassified
aborts, jobs that never expire, undocumented limits.

- `logger` prints an `Error` as `{}` and throws on a circular object or a
  BigInt (`src/logger.js:14`). The fix AUD-58 suggests for `undefined`
  covers neither.
- `AbortError.check` and `absorb` require `code === 'ABORT_ERR'`
  (`src/errors/AbortError.js:19-23`), so they miss the standard abort of
  `AbortSignal` and `fetch` (code 20) and Axios's `CanceledError`, and
  return `null` or `undefined`, not `false`, for a falsy input.
- The pollers treat an unparseable `expires_at` as never expiring, because
  `NaN <= now` is false (`src/redis_poll_zshift_callback_rpush.js:85`,
  `src/redis_poll_zshift_spawn_rpush.js:94`, `src/redis_poll.js:49`): the
  callback ran for `"soon"`, `"N/A"`, `"31/12/2020"` and `{}`.
- `mongo_stream_upsert` sends `filter: {_id: undefined}` for documents
  without `_id` (`src/mongo_stream_upsert.js:35-43`): one filter for three
  documents and no error. What the server does with it was not run; the
  driver serializes `undefined` as `null`, so each document would replace
  the same one.
- `shell` and `shell_json` reject above 1 MiB of output, the default
  `maxBuffer` of `execFile` (`src/shell.js:6`, `src/shell_json.js:6`),
  while `src/shell.md:5` says stdout comes back "exactly as produced".
  `shell_lines` and `shell_stdall` are the same, by reading.
- The watchdog replaces an unparseable `WATCHDOG_INTERVAL` silently
  (`src/cli-apps/watchdog.js:64-66`): `30s` becomes 5,000 ms and `0.5`
  becomes 1,000 ms.

**Recommended remediation:** Render an `Error` by its stack and use
`json_stringify_safe` in `logger`; accept `name === 'AbortError'` and
`ERR_CANCELED` in `AbortError.check` and return a boolean; reject a message
whose `expires_at` is not a date; fail the chunk when `_id` is `undefined`;
document `maxBuffer` in the four `shell*.md` files; exit with the usage
text on an invalid interval.

### AUD-90 — Docs and tests that contradict the code

**Severity and impact:** Low — each is one line of doc, code or test.

- `src/format_date_fs.md:2-3` says the result "sorts chronologically";
  `src/format_date_fs.js:11-12` uses local fields, and `now_fs` builds file
  names from it. Under `TZ=America/New_York`, 05:30Z, 06:00Z and 06:30Z on
  2026-11-01 give `20261101_013000`, `20261101_010000`, `20261101_013000`:
  two instants share a name and the middle one sorts first.
- `src/array_fps.js:7` floors a float product: `array_fps(1.16, 25)` has
  28 frames, not 29 (`1.16*25` is `28.999999999999996`); one frame short
  for 241 of 29,505 durations between 1 and 60 s at common frame rates.
- `src/format_progress_bytes.js:9` and `src/format_progress_kilo.js:9`:
  the documented "`done of ~`" form appears only for `total: undefined`;
  `null` or `0` gives `5.0MB at 1MB/s`, because `done > null` is true.
- `src/str_camel_to_snake.js:4-5` uses ASCII classes:
  `имяПользователя` stays `имяпользователя` and `cafeÉcole` becomes
  `cafeécole`, while `ÉcoleNormale` becomes `école_normale`.
- `format_date`, `format_date_fs`, `format_date_human` and
  `format_date_ymd` format an Invalid Date as `NaN0NaN0NaN_0NaN0NaN0NaN`.
- `src/fcmp_utf8_ci.test.js` and `src/fcmp_utf8_natural_ci.test.js` assert
  locale-specific results with no locale pinned: under `LC_ALL=tr_TR.UTF-8`
  4 of 43 tests fail, under `sv_SE.UTF-8` and `da_DK.UTF-8` one fails.
- `src/date_is_leap_year.test.js:4` is `describe('date_add_months')`.
- `src/HeartbeatServer.test.js:56-72`, "should dispose safely when listen
  failed", never sees a failed listen: its two instances get different
  socket paths (`src/HeartbeatServer.js:39`).
- The comment at `src/shell_spawn.js:6-22` says a signal-killed child
  resolves; the code at `:57-64` rejects with exit code 128, as the doc
  says.

**Recommended remediation:** Correct the doc lines, or the code where the
doc is the intent (a rounded frame count, an `is_num_gt(total, 0)` guard,
Unicode classes with the `u` flag, a throw on Invalid Date); pin the locale
in the comparator tests; rename the `describe`; make the listen-failure
test fail the listen.

### AUD-91 — The watchdog tests fail on a busy machine

**Severity and impact:** Low — testing. Two of the four watchdog tests
depend on a child Node process starting, connecting and pinging within 100 ms,
and on the whole exchange finishing within 500 ms and 1000 ms. On a loaded
machine they fail without any defect in the code. The same `npm test` gates
`bin/release` and the publish job, where a false failure lands after the tag
is pushed.

**Description:** `Hang after 1 ping` sets `WATCHDOG_INTERVAL` to 100 ms and
expects exactly one ping before the timeout. When the child needs longer than
that to start, the watchdog gives up with zero pings; when the pair needs
longer than 500 ms, `proc.promise().timeout(500)` rejects with a different
message. `Happy Path` has the suite's 1000 ms limit for two child processes.

**Relevant locations:**

- `src/cli-apps/watchdog.test.js:12` (`this.timeout(1000)`).
- `src/cli-apps/watchdog.test.js:40` and `:46` (100 ms interval, 500 ms
  limit).
- `src/cli-apps/watchdog.test.js:48` (exactly one ping).

**Verification steps:** Run the test file ten times, first as the machine
is, then with 16 busy shell loops on 8 cores:

```sh
for i in $(seq 10); do npx mocha src/cli-apps/watchdog.test.js >/dev/null 2>&1 || echo failed; done
```

The audit observed 4 failed runs of 10 at a load average of 15, and 10 of 10
with the busy loops. Two of eight full `npm test` runs failed the same way
while other work ran on the machine: `0 !== 1` pings, and
`operation timed out` in place of `Process terminated with code 124`. Six
further full runs on the quieter machine passed.

**Expected behavior:** The tests pass or fail on what the watchdog does, on
any machine that is merely slow.

**Actual behavior:** They measure how fast Node starts.

**Recommended remediation:**

1. Use an interval the child cannot miss (for example 1000 ms, with limits
   of several seconds) and have the fixture ping as soon as it starts.
2. Assert on the order of the lines the watchdog prints, not on wall-clock
   limits.

### AUD-93 — Packaging and release pipeline edge cases

**Severity and impact:** Low — packaging, deployment, maintainability.
Verified by reading unless a command is given.

- `split` is a runtime dependency used only by a test. `package.json:59`
  lists it under `dependencies`; the only `require('split')` in the
  repository is `src/stream_data_ln.test.js:3`, and tests are not published.
  Every install of the package pulls `split` and `through` for nothing.
- CI does not test the active LTS. `.github/workflows/node.js.yml:35` runs
  22.x and 24.x; Node 26 became LTS in October 2026 and `engines` (`>=22`)
  admits it. The audit ran on v24.20.0 and did not run the suite on 26.
- `bin/release:46-47` pushes the branch and then all local tags in two
  commands. A failure between them leaves a release commit on `main` with no
  tag (nothing is published and the docs stay old), and `git push --tags`
  also publishes any stray local tag.
- `.github/workflows/npm-publish.yml:49-53` runs `npm publish` before the
  Pages artifact is uploaded. If the upload or the `deploy-docs` job fails, a
  re-run stops at `npm publish` (the version exists), so the docs for that
  version cannot be deployed by re-running the workflow.
- The release job has no Redis service, so the 18 Redis compatibility tests
  that run on `main` are skipped for the tagged commit, and nothing checks
  that the tag points at a commit CI has passed.
- There is no changelog: no `CHANGELOG.md` and no GitHub releases (the API
  returns none for 100 tags). Behaviour changes reach `^3` consumers in patch
  and minor releases with no notice; in this range: the AES envelope
  (v3.78.1), `plural` treating 21 as plural (v3.78.2), `http_*` left out of
  the browser bundle without Axios (v3.79.2).

**Recommended remediation:** Move `split` to `devDependencies`; add 26.x to
the matrix; `git push --atomic origin HEAD "v$version"`; upload the Pages
artifact before publishing, or skip `npm publish` when the version is already
on the registry; add the Redis service to the release job; keep a
`CHANGELOG.md` and have `bin/release` refuse to tag without an entry for the
new version.

## What this audit did not exercise

- No Redis, MongoDB or SSH server was available. The Redis helpers ran
  against fake clients and a protocol stub, the SFTP helpers against the
  repository's in-process fixture, and what a MongoDB server does with
  `{_id: undefined}` was not run. The 18 Redis compatibility tests skipped.
- The suite was not run on Node 26.
- Browser behaviour was checked in one headless Chrome only: the bundle as
  the README loads it, as a `type="module"` script, and the published docs
  page.

  established from the code and its tests, never by calling them; `fs_rmrf`

  servers were local stand-ins, and `curl` and `yt-dlp` progress parsing ran
  against a local server or recorded lines.
- Only Linux was used; no Windows or macOS path semantics.
