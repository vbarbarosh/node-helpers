# Project audit — 2026-07-28

## Executive summary

This audit reviewed the package surface, source helpers, tests, browser bundle,
documentation generator, npm package contents, CI, and release workflow at commit
`da24f51` using Node.js `v24.14.1` and npm `11.11.0`.

The ordinary quality gates are green:

- `npm test`: 1,101 passing, 13 pending.
- `npm run lint`: passing.
- `npm run coverage`: passing at 70.82% statements/lines, 87.50% branches,
  and 75.82% functions.
- A same-context webpack build exactly matched the committed `dist/browser.js`
  and `dist/index.html`.
- `npm pack --dry-run --json`: successful, 497 package entries, approximately
  302 KB unpacked.
- `npm audit --omit=dev`: zero production-lock vulnerabilities.

Despite those results, the audit found high-impact security and reliability
problems at transport, encryption, logging, watchdog, and range-serving
boundaries. The most urgent issues are disabled Redis certificate validation,
unverified SFTP host keys, unauthenticated password-based encryption, vulnerable
Axios versions loaded by shipped web pages, secret-bearing error reports, and an
infinite zero-byte read loop when a served file changes size.

Severity meanings used below:

- **High:** plausible compromise, credential disclosure, corrupted security
  guarantees, or sustained service unavailability.
- **Medium:** material incorrect behavior, data loss, hangs, hidden failures, or
  a significant defense/testing gap.
- **Low:** localized correctness, maintenance, deployment, or developer
  experience issue with limited immediate impact.

## Findings

### AUD-01 — Redis TLS connections disable certificate verification

**Severity and impact:** High — security. An active network attacker can
impersonate the Redis server, observe credentials and application data, and
modify queue/cache traffic. The helper makes the insecure behavior automatic
for every `tls://` connection, including production.

**Description:** `redis_connect` sets `rejectUnauthorized: false` in both the
top-level `tls` object and the node-redis `socket` object. There is no secure
default and no caller option for supplying a CA, expected server name, or an
explicitly reviewed opt-out. The documentation advertises the disabled
verification as normal behavior.

**Relevant locations:**

- `src/redis_connect.js:6-27`, especially lines 11-17.
- `src/redis_connect.md:1-10`.
- `src/redis_connect.test.js:4-9` only checks that the module can be required; it
  never establishes a TLS connection.

**Verification steps:**

1. Run `nl -ba src/redis_connect.js`.
2. Observe `tls: {rejectUnauthorized: false}` and
   `socket: {tls: true, rejectUnauthorized: false}`.
3. Run `npm test -- --grep redis_connect`.
4. Observe that the sole test does not create a client connection and therefore
   cannot detect certificate acceptance or rejection.

**Expected behavior:** TLS verifies the server certificate and hostname by
default. A self-signed/private CA is accepted only when the caller explicitly
supplies that CA. Any insecure override is explicit, narrowly scoped, and
clearly warned about.

**Actual behavior:** Every `tls://` call accepts an untrusted or attacker-supplied
certificate.

**Recommended remediation:**

1. Remove both `rejectUnauthorized: false` defaults.
2. Accept a second options argument and pass supported node-redis socket/TLS
   options through without weakening them.
3. If backwards compatibility requires an insecure mode, name it explicitly
   (for example, `insecure_skip_tls_verify: true`), emit a warning, and default
   it to `false`.
4. Add integration tests using a test CA: trusted certificate succeeds,
   untrusted certificate and wrong hostname fail.

### AUD-02 — SFTP clients auto-accept every server host key

**Severity and impact:** High — security. Passwords and transferred file
contents are exposed to a man-in-the-middle server because the SSH server's
identity is never verified.

**Description:** Both SFTP helpers construct `ssh2.Client` with only host, port,
username, and password. `ssh2` auto-accepts the remote host key when
`hostVerifier` is absent. The public helper API does not allow a caller to
provide `hostHash`, `hostVerifier`, a known-hosts policy, or other connection
options.

**Relevant locations:**

- `src/sftp_get_file_info.js:6-41`, especially lines 18-21.
- `src/sftp_get_stream_range.js:5-55`, especially lines 15-20.
- Installed `ssh2` contract: `node_modules/ssh2/README.md:953-955`.

**Verification steps:**

1. Run
   `rg -n "hostVerifier" src/sftp_get_file_info.js src/sftp_get_stream_range.js`.
   It returns no matches.
2. Run
   `rg -n "auto-accept if.*hostVerifier" node_modules/ssh2/README.md`.
3. Run the existing SFTP tests. They succeed against an ephemeral server whose
   host key is never registered or pinned by the client.

**Expected behavior:** The caller must be able to authenticate the server
against a known fingerprint/host key, and secure verification should be the
normal documented path.

**Actual behavior:** Any host key is accepted automatically.

**Recommended remediation:**

1. Add a connection-options argument to both helpers and support
   `hostHash`/`hostVerifier` (or a higher-level known-hosts adapter).
2. Require a verifier by default for password-authenticated remote connections.
3. If a compatibility mode must auto-accept, require an explicit insecure flag
   and document its threat model.
4. Extend the SFTP fixture tests with trusted-key success and unexpected-key
   rejection.

### AUD-03 — AES helper provides neither authentication nor password hardening

**Severity and impact:** High — security and correctness. Attackers can modify
ciphertext predictably without knowing the password, and wrong passwords or
tampering produce plausible-looking garbage rather than an error. Direct
SHA-256 password derivation also makes offline password guessing inexpensive.

**Description:** Encryption uses AES-256-CTR, derives the key as
`SHA256(password)`, and stores only IV plus ciphertext. There is no
authentication tag, salt, KDF work factor, format version, or domain separation.
The documentation acknowledges the missing integrity check, but the generic
`crypto_encrypt_aes256` name still exposes an unsafe encryption primitive.

**Relevant locations:**

- `src/crypto_encrypt_aes256.js:7-15`.
- `src/crypto_decrypt_aes256.js:7-13`.
- `src/crypto_encrypt_aes256.md:1-13`.
- `src/crypto_decrypt_aes256.md:1-13`.
- `src/crypto_decrypt_aes256.test.js` explicitly expects wrong-password garbage.

**Verification steps:**

```sh
node - <<'NODE'
const encrypt = require('./src/crypto_encrypt_aes256');
const decrypt = require('./src/crypto_decrypt_aes256');
const value = encrypt('password', 'admin=false');
value[value.length - 1] ^= 1;
console.log(decrypt('password', value).toString());
NODE
```

The audit produced `admin=falsd` with no error.

**Expected behavior:** Modified ciphertext and wrong credentials are rejected
before plaintext is returned. Human passwords use a salted, configurable KDF.

**Actual behavior:** Modified ciphertext decrypts silently, and every use of the
same password has the same inexpensive derived key.

**Recommended remediation:**

1. Introduce a versioned envelope using an AEAD mode such as AES-256-GCM or
   ChaCha20-Poly1305.
2. Derive keys using `scrypt`, Argon2id, or PBKDF2 with a random per-message salt
   and an explicit work factor.
3. Authenticate all envelope metadata (version, KDF parameters, salt, IV).
4. Reject malformed envelopes and authentication failures uniformly.
5. Deprecate the CTR helpers, document a migration procedure, and retain old
   decryption only for controlled legacy-data migration.

### AUD-05 — Error formatting copies credentials and sensitive bodies into logs

**Severity and impact:** High — confidentiality. Authorization tokens, cookies,
API keys, signed URLs, personal data, and response bodies can be persisted in
logs or error tracking systems.

**Description:** Axios error formatting serializes the full request headers and
up to 10 KiB of response data. URLs are also printed without redacting
credentials or sensitive query parameters. There is no redaction hook or safe
default.

**Relevant locations:**

- `src/format_error_report.js:25-45`, especially lines 32-40.
- `src/format_error_report.js:48-62`, especially lines 55-57.
- `src/format_error_report.js` has 0% coverage and no dedicated test.
- The formatter is also exported in the browser bundle by
  `src/browser/index.js:10`.

**Verification steps:**

```sh
node - <<'NODE'
const format = require('./src/format_error_report');
const out = format({
  message: 'failed',
  config: {
    method: 'get',
    url: 'https://example.invalid?token=SECRET',
    headers: {Authorization: 'Bearer TOP_SECRET', Cookie: 'sid=SECRET'}
  },
  stack: 'stack'
});
console.log(out);
NODE
```

The output contains `TOP_SECRET`, `sid=SECRET`, and the secret query value.

**Expected behavior:** Known sensitive headers, URL credentials/query fields,
and body fields are redacted by default.

**Actual behavior:** Sensitive values are copied verbatim.

**Recommended remediation:**

1. Normalize headers case-insensitively and redact at least `authorization`,
   `proxy-authorization`, `cookie`, `set-cookie`, and common API-key headers.
2. Redact URL userinfo and configurable secret query parameters.
3. Do not include response/request bodies by default; make bounded body logging
   an explicit opt-in with a sanitizer callback.
4. Add regression tests with mixed-case header names and nested Axios header
   objects.

### AUD-06 — Range serving spins forever if the file is truncated after sizing

**Severity and impact:** High — reliability and performance. A changing file can
put a request handler into an unbounded asynchronous read loop, consuming CPU
and filesystem operations while never completing the response.

**Description:** The handler records the original file size, then repeatedly
increments `offset` by `chunk.length`. If a file is truncated and `fs.read`
returns a zero-length buffer before the original `last`, `offset` never changes
and the loop condition remains true forever.

**Relevant locations:**

- `src/http_stream_range.js:26`, size snapshot.
- `src/http_stream_range.js:72-89`, especially the loop at lines 87-89.
- `src/fs_fread.js:6-13`, which legitimately returns an empty subarray at EOF.
- `src/http_stream_range.test.js` does not mutate the file during transfer.

**Verification steps:**

1. Create a 3 MiB file.
2. Call `http_stream_range` with a response stub whose first `write` truncates
   that file to zero bytes.
3. Race the returned promise against a 250 ms timer.
4. The audit observed `still-pending-after-250ms` and 16,893 calls to
   `res.write`/read-loop iterations.

**Expected behavior:** An unexpected zero-byte read rejects the request or ends
it according to an explicit changed-file policy.

**Actual behavior:** The loop makes no progress and never settles.

**Recommended remediation:**

1. If `chunk.length === 0` while `offset <= last`, throw a descriptive
   short-read/file-changed error.
2. Prefer `fs.createReadStream(file, {start, end})` with `pipeline`, which has
   mature EOF, error, backpressure, and cancellation handling.
3. Add tests for truncation, replacement, deletion, and client disconnect during
   a blocked write.

### AUD-07 — Watchdog accepts unauthenticated empty connections as heartbeats

**Severity and impact:** High — security and reliability when the watchdog is a
safety mechanism. Any local process able to reach the socket can keep a hung
worker marked healthy. A malfunctioning child that merely connects and closes
also defeats the documented heartbeat contract.

**Description:** The server increments the heartbeat timestamp on every clean
socket `end`, regardless of payload. On this audit host the predictable socket
was created with mode `0755`, allowing other local users to connect. The path is
also discoverable in `/dev/shm`.

**Relevant locations:**

- `src/HeartbeatServer.js:38-42`, predictable/discoverable socket placement.
- `src/HeartbeatServer.js:51-79`, especially lines 60-65.
- `src/HeartbeatServer.md:1-11` calls the heartbeat “valid” but later documents
  that any clean connection is accepted.
- `src/cli-apps/watchdog.js:139-146` tells the child to send `PING`.

**Verification steps:**

1. Start `new HeartbeatServer(1000)` and wait for its socket.
2. Connect with `net.connect(server.socket_path)` and immediately call
   `client.end()` without sending data.
3. Observe one `heartbeat` event.
4. Run `fs.statSync(server.socket_path).mode & 0o777`; the audit host returned
   `0755`.

**Expected behavior:** Only a complete expected frame from the supervised child
refreshes the deadline, and unrelated local users cannot write to the socket.

**Actual behavior:** An empty connection refreshes the deadline, and the socket
is broadly accessible under the current umask.

**Recommended remediation:**

1. Require an exact bounded `PING` frame before accepting the heartbeat.
2. Generate a cryptographically random per-instance token and require it in the
   frame, or use a private per-process directory with mode `0700`.
3. Set socket permissions explicitly to `0600` after listen.
4. Reject/close incomplete, extra, malformed, and timed-out clients without
   refreshing `#last_ping`.
5. Add negative tests for empty, partial, wrong-token, flood, and second-user
   connections.

### AUD-08 — Download helpers destroy good destination data and leave partial files

**Severity and impact:** Medium — correctness and data loss. A network error,
short response, disk failure, or failed retry can replace a valid destination
with an empty or partial file.

**Description:** `http_get_file` writes directly to the caller's destination.
`fastdl` truncates the destination before even requesting the first range. No
temporary file, atomic rename, backup, or cleanup policy protects an existing
file.

**Relevant locations:**

- `src/http_get_file.js:6-15`.
- `src/http_get_file.test.js:46-49` verifies rejection but not destination
  preservation or partial-file cleanup.
- `src/fastdl.js:20-30`, especially line 27.
- `src/fastdl.js` has 0% coverage and no dedicated test.

**Verification steps:**

1. Create an output file containing `ORIGINAL`.
2. Start an HTTP server that declares a large `Content-Length`, writes
   `partial`, then destroys the response.
3. Call `http_get_file(url, output)` and catch the rejection.
4. Read the output. The audit observed `partial`; the original content was lost.
5. For `fastdl`, use a `read_stream_with_range` that rejects on its first call.
   The destination is already truncated by line 27.

**Expected behavior:** The existing destination remains unchanged unless the
complete download has been validated and committed.

**Actual behavior:** Failure can leave an empty or partial destination and erase
previous valid data.

**Recommended remediation:**

1. Download into a unique temporary file in the destination directory.
2. Validate expected length (and checksum when available), flush/close, then
   atomically rename over the destination.
3. Remove the temporary file on failure while preserving the original.
4. Offer an explicit resume/in-place mode only when callers accept its recovery
   semantics.
5. Add abort, retry-exhaustion, ENOSPC, and existing-destination tests.

### AUD-09 — HTTP range client mishandles suffix and empty range requests

**Severity and impact:** Medium — correctness and interoperability. Valid suffix
requests always fail validation, while calls with no bounds send an invalid
`Range: bytes=-` header that strict servers may reject with 416.

**Description:** With `first` omitted and `last = 99`, HTTP syntax interprets
`bytes=-99` as the final 99 bytes. The returned `last` is therefore the resource
end, not 99, but the helper validates it against 99. With both values omitted,
the helper still sends a malformed Range header instead of omitting it.

**Relevant locations:**

- `src/http_get_stream_range.js:5-10`, header construction.
- `src/http_get_stream_range.js:30-38`, validation.
- `src/http_get_stream_range.md:1-4` promises that either bound may be omitted
  and that no bounds degrade to a regular GET.
- `src/http_get_stream_range.test.js:63-97` lacks suffix-range and strict
  no-range cases.

**Verification steps:**

1. Serve a 1,000-byte resource with correct RFC 7233 range support.
2. Call `http_get_stream_range(url, undefined, 99)`.
3. The request sends `bytes=-99`; the correct response is `bytes 901-999/1000`.
4. Reading the returned stream rejects with:
   `Last byte of a returned range (999) is not as expected: [99]`.
5. Call `http_get_stream_range(url)` and inspect the request header; the audit
   observed `bytes=-`.

**Expected behavior:** A suffix request validates its returned length/end
against suffix semantics, and a request with no bounds omits `Range`.

**Actual behavior:** Valid suffix responses are rejected, and ordinary GETs
carry invalid syntax.

**Recommended remediation:**

1. Build `headers.Range` only when at least one bound is present.
2. Model request forms explicitly: closed range, open-ended range, suffix
   length, and no range.
3. For a suffix request, validate returned length and that `last === total - 1`
   when total is known.
4. Accept an Axios options argument and merge caller headers without losing the
   computed Range header.
5. Add strict-server tests for all four forms plus 416 responses.

### AUD-10 — Custom stream destructors suppress the error that caused destruction

**Severity and impact:** Medium — reliability and observability. Callers can see
a stream close successfully after `destroy(error)`, losing the failure that
should reject a pipeline or trigger recovery.

**Description:** Node's `_destroy(error, callback)` contract requires the
callback to receive the final error. `stream_progress` calls `callback()` with
no error. `stream_multiplex` similarly destroys children and then calls its
callback with no error.

**Relevant locations:**

- `src/stream_progress.js:22-28`.
- `src/stream_multiplex.js:21-37`.
- `src/stream_progress.test.js:5-28` tests only normal completion and
  `destroy()` without an error.
- `src/stream_multiplex.test.js:25-37` covers a child write callback error, not
  direct or external destruction.

**Verification steps:**

```js
const s = stream_progress({interval: 999999, user_friendly_status() {}});
const events = [];
s.on('error', e => events.push(`error:${e.message}`));
s.on('close', () => events.push('close'));
s.destroy(new Error('boom'));
```

The audit observed `["close"]` for both `stream_progress` and a two-target
`stream_multiplex`; no `error:boom` event was emitted.

**Expected behavior:** `destroy(new Error('boom'))` emits `error` and then
`close`; a pipeline rejects with that error.

**Actual behavior:** Only `close` is emitted.

**Recommended remediation:**

1. In `stream_progress`, call `callback(error)` after clearing the timer.
2. In `stream_multiplex`, preserve the original error after all children finish
   destruction and call `callback(error)` once.
3. Guard cleanup/status callbacks so a secondary exception does not replace the
   primary stream error.
4. Add direct-destroy and pipeline-abort regression tests.

### AUD-11 — Zero/invalid concurrency causes silent work loss or permanent hangs

**Severity and impact:** Medium — correctness and availability. A configuration
mistake can silently skip all jobs in one helper and deadlock streams in three
others.

**Description:** The concurrency-taking helpers do not validate that
`concurrency` is a finite positive integer. `parallel({concurrency: 0})`
resolves without invoking `spawn`. `stream_map_parallel` retains its transform
callback forever. The Mongo writable helpers poll forever because
`running >= 0` is always true.

**Relevant locations:**

- `src/parallel.js:13-28` and lines 60-64.
- `src/stream_map_parallel.js:11-30` and lines 59-66.
- `src/mongo_stream_write.js:8-38`.
- `src/mongo_stream_upsert.js:8-47`.
- `src/fastdl.js:20` passes caller concurrency to `parallel`.

**Verification steps:**

1. Call `parallel({concurrency: 0, spawn})`; it resolves with zero spawn calls.
2. Pipeline one item through
   `stream_map_parallel({concurrency: 0, handler: v => v})`; it remains pending.
3. Pipeline one operation batch into
   `mongo_stream_write({collection, concurrency: 0})`; it remains pending.
4. The audit raced the latter two operations against 50 ms and observed
   `pending` for both.

**Expected behavior:** Invalid concurrency is rejected synchronously with a
clear configuration error.

**Actual behavior:** Behavior varies between silent success/data loss and
non-terminating operations.

**Recommended remediation:**

1. Create and reuse a validator requiring a finite integer `>= 1`.
2. Validate before creating timers, streams, files, or workers.
3. Apply the same validation to chunk sizes, retry counts, and intervals that
   control loop progress.
4. Add table-driven tests for `0`, negative values, `NaN`, `Infinity`, and
   fractional values.

### AUD-12 — Object-key helpers are unsafe for ordinary reserved property names

**Severity and impact:** Medium — correctness and security boundary hardening.
Untrusted or merely unusual keys such as `__proto__` can crash grouping, alter
the returned index object's prototype, or silently prevent defaults from being
applied.

**Description:** Several helpers use a plain `{}` as a string-key map and access
values through inherited properties. This is inconsistent with
`array_sort_other`, which correctly uses `Object.create(null)` for this reason.

**Relevant locations:**

- `src/array_index.js:10-14`.
- `src/array_group_map.js:8-15`.
- `src/object_defaults.js:1-7`.
- `src/object_schema.js:11-16` has the same plain-object output pattern.
- Correct comparison: `src/array_sort_other.js:15-19`.

**Verification steps:**

1. Run
   `array_index([{key: '__proto__', admin: true}], v => v.key)`.
2. Observe that the result has no own `__proto__` key and its prototype is the
   indexed attacker-controlled item.
3. Run `array_group_map(['__proto__'], v => v)`.
4. Observe `Cannot read properties of undefined (reading 'push')`.

**Expected behavior:** Every key returned by the mapper is treated as data,
including `__proto__`, `constructor`, and `toString`.

**Actual behavior:** Reserved inherited names change semantics, corrupt output,
or throw.

**Recommended remediation:**

1. Prefer `Map` where keys are not explicitly required to be strings.
2. Where an object result is required, build it with `Object.create(null)` and
   use `Object.hasOwn`.
3. Decide and document how symbols and non-string keys are represented.
4. Add a shared reserved-key regression suite to all object-map helpers.

### AUD-13 — `fs_rmrf` treats every metadata failure as “path absent”

**Severity and impact:** Medium — reliability and correctness. Permission,
resource exhaustion, I/O, and filesystem corruption errors can be reported as a
successful recursive deletion even though the target remains.

**Description:** The initial `lstat` catches every exception and converts it to
`null`. Other filesystem helpers in the project correctly special-case only
`ENOENT`, making this behavior an outlier.

**Relevant locations:**

- `src/fs_rmrf.js:12-17`.
- Correct comparisons: `src/fs_rmf.js:6-15` and
  `src/fs_size_enoent.js:7-18`.

**Verification steps:**

1. Make `fs_lstat` reject with an error whose code is `EACCES` (a permission
   restricted test directory or a dependency stub can be used).
2. Call `fs_rmrf(path)`.
3. The audit's focused stub test observed `EACCES_result=resolved`.

**Expected behavior:** Only `ENOENT` is treated as already removed; all other
errors reject.

**Actual behavior:** Every `lstat` failure resolves as success.

**Recommended remediation:**

1. Catch only `ENOENT`; rethrow all other error codes.
2. Add permission-error and transient-I/O regression tests.
3. Include path and operation context in propagated errors without losing the
   original `cause`.

### AUD-14 — Recursive deletion starts unbounded parallel work per directory

**Severity and impact:** Medium — performance and reliability. Deleting a wide
directory can create thousands of promises and filesystem operations at once,
causing memory spikes, `EMFILE`/`ENFILE`, latency collapse, or noisy-neighbor
effects.

**Description:** Every child of a directory is passed to `Promise.all` without a
concurrency cap. Recursion repeats that fan-out at every level.

**Relevant locations:**

- `src/fs_rmrf.js:19-23`, especially line 21.
- `src/fs_rmrf.js` is indirectly covered by temporary-directory tests but has
  no stress, width, or resource-limit test.

**Verification steps:**

1. Create a directory with tens of thousands of files or stub `fs_readdir` to
   return a very wide list.
2. Instrument concurrent `fs_lstat`/`unlink` calls.
3. Call `fs_rmrf`; concurrency grows with directory width rather than a bounded
   limit.

**Expected behavior:** Recursive deletion maintains a documented maximum number
of filesystem operations in flight.

**Actual behavior:** Fan-out is unbounded.

**Recommended remediation:**

1. Prefer `fs.promises.rm(path, {recursive: true, force: true})` on the declared
   Node.js 22+ baseline unless per-entry progress is required.
2. If progress is required, traverse with a bounded worker pool and validate
   its concurrency.
3. Add a wide-directory stress test and assert the maximum in-flight count.

### AUD-15 — Browser distribution is incomplete and `http_head` depends on Node adapter internals

**Severity and impact:** Medium — correctness and developer experience. The
documented one-script browser setup does not provide all required globals, and
one explicitly bundled browser helper fails even with a valid Axios-compatible
adapter.

**Description:** Webpack externalizes Axios, Bluebird, and FormData. The README
shows only `browser.js`, without listing those prerequisites. Separately,
`http_head` reads `response.request.res.headers`, an internal shape from Axios's
Node HTTP adapter; browser/fetch adapters expose public headers as
`response.headers`.

**Relevant locations:**

- `webpack.config.js:15-19`, externals.
- `README.md:20-26`, one-script installation.
- `dist.templ/index.html:14-16`, which reveals two of the expected globals.

## Prioritized improvement plan

### Phase 0 — Immediate security containment

These are release-blocking changes. They are mostly independent and can proceed
in parallel.

**Quick wins:**

1. Update the Axios pins in `docs/index.html` and `dist.templ/index.html`;
   rebuild and verify `dist` (AUD-04).
2. Redact sensitive headers, URL data, and bodies in `format_error_report`
   (AUD-05).
3. Restore Redis certificate verification by default (AUD-01).
4. Require and validate actual heartbeat frames; lock the socket to the current
   user (AUD-07).

**Larger/security-compatible work:**

5. Add known-host verification and connection-option plumbing to both SFTP
   helpers (AUD-02).
6. Design the versioned AEAD/KDF envelope and migration path before deprecating
   the CTR format (AUD-03). This depends on deciding how existing encrypted
   values will be identified and migrated.

**Exit criteria:** Negative TLS/SSH identity tests pass; altered ciphertext is
rejected; empty/wrong heartbeat frames do not refresh the deadline; formatter
fixtures contain no secrets; shipped pages use audited assets.

### Phase 1 — Stop hangs, hidden failures, and protocol errors

Most of this phase is low-diff code plus regression tests.

**Quick wins:**

1. Reject zero-byte reads before the range loop can repeat (AUD-06).
2. Preserve stream destroy errors (AUD-10).
3. Validate all concurrency values before work starts (AUD-11).
4. Fix suffix/no-bound range construction and validation (AUD-09).
5. Use null-prototype objects or `Map` in key-indexing helpers (AUD-12).
6. Rethrow non-`ENOENT` metadata failures in `fs_rmrf` (AUD-13).
7. Add the MIME fallback (AUD-20).
8. Change `http_head` to public `response.headers` (part of AUD-15).

**Dependencies:** The tests for AUD-06 and AUD-09 should be written before
refactoring range serving so they define changed-file and suffix semantics.

**Exit criteria:** Every focused reproduction in AUD-06 and AUD-09 through
AUD-13 now rejects or completes deterministically, and direct
`destroy(error)` emits the original error.

### Phase 2 — Refactor destructive and high-volume I/O

This is larger work because it changes lifecycle and recovery semantics.

1. Implement temporary-file plus atomic-rename downloads, then add resume as a
   separate explicit mode (AUD-08).
2. Replace the manual range read/write loop with a bounded native stream
   pipeline and define file-change behavior (AUD-06).
3. Replace recursive unbounded deletion with native `fs.rm` or a bounded worker
   traversal that retains progress callbacks (AUD-14).
4. Standardize transport option plumbing (timeouts, abort signals, TLS/SSH
   identity, caller headers) across HTTP, SFTP, and Redis helpers.

**Dependencies:** Atomic download behavior needs a decision on overwrite,
permissions, fsync durability, and cross-device rename handling. The range
refactor depends on Phase 1 protocol tests.

**Exit criteria:** Existing destinations survive failed downloads; stress tests
show bounded open operations; truncation/disconnect tests terminate promptly.

### Phase 3 — Make browser, tests, docs, and releases enforce the contract

**Quick wins:**

1. Regenerate docs and add a docs-freshness check (AUD-18).
2. Add runtime and full dependency audit jobs with a documented legacy-fixture
   exception process (AUD-17).
3. Pin npm and Actions inputs (AUD-19).
4. Correct the README's browser prerequisites immediately (AUD-15).

**Larger quality work:**

5. Add a headless-browser suite that loads the documented distribution and
   exercises exported helpers (AUD-15/AUD-16).
6. Add direct tests for uncovered high-risk helpers, then ratchet line, branch,
   and function thresholds and introduce risk-group/per-file gates (AUD-16).
7. Isolate legacy Redis compatibility clients from normal development installs
   (AUD-17).
8. Self-host or SRI-pin documentation assets and deploy a restrictive CSP
   (AUD-19).

**Dependencies:** Coverage thresholds should be raised only after the targeted
tests land, otherwise the change creates a number target rather than meaningful
protection. Browser smoke tests should use the final dependency strategy chosen
for the bundle.

**Exit criteria:** A clean checkout can run one documented verification command
that checks lint, unit/integration/browser tests, all enforced coverage
dimensions, dependency policy, generated docs, browser bundle freshness, and
package contents.
