Severity meanings are the same as in the previous audit:

- **High:** plausible compromise, credential disclosure, corrupted security

- **Medium:** material incorrect behavior, data loss, hangs, hidden failures, or

- **Low:** localized correctness, maintenance, deployment, or developer

## New findings

### AUD-21 — Process helpers pass `0`, `1`, and `-1` straight to `kill(2)`

**Severity and impact:** Medium — security and availability. `kill(0, sig)`
signals the caller's own process group and `kill(-1, sig)` signals every
process the user may signal. A caller that computes a pid from a failed spawn
(`proc.pid ?? 0`) or from an unvalidated input terminates itself, its siblings,
or in the worst case everything the user owns, instead of receiving an error.

**Description:** None of the four process helpers validate their argument
before calling `process.kill`. The exists helpers report `true` for these
pseudo-pids, and the kill helpers send real signals to them.

**Relevant locations:**

- `src/pid_kill_grace.js:11` and `:32`.
- `src/pgid_kill_grace.js:12` and `:33`.
- `src/pid_exists.js:5`.
- `src/pgid_exists.js:6`.

**Verification steps:**

```sh
node -e "(async () => {
  console.log(await require('./src/pid_exists')(0), await require('./src/pid_exists')(-1),
              await require('./src/pgid_exists')(0), await require('./src/pgid_exists')(1));
})()"
```

The audit observed `true true true true`. Running
`require('./src/pgid_kill_grace')(0, {log: console.log})` printed
`Terminating process group 0: sending SIGTERM` and the Node process killed
itself. The `-1` case was verified only with signal 0.

**Expected behavior:** Non-integer, non-positive, or reserved ids (`0`, `1`,
negatives) are rejected with a `TypeError` before any signal is sent.

**Actual behavior:** The value reaches the kernel unchanged.

**Recommended remediation:**

1. Add `if (!Number.isInteger(pid) || pid <= 1) throw new TypeError(...)` to
   all four helpers (`pgid <= 1` for group helpers).
2. Add tests for `0`, `1`, `-1`, `NaN`, `1.5`, and `undefined`.

### AUD-22 — `urlparts` reports a different host than browsers when the authority contains a backslash

**Severity and impact:** Medium — security. WHATWG parsers (browsers, Node's
`URL`, Axios via Node) treat `\` as `/` for special schemes. Any code that uses
`urlparts(...).host` for an allow-list, redirect-target, or SSRF check accepts
a URL that the HTTP client then sends to a different host.

**Description:** The authority ends at the first `/` only, and userinfo is split
on the last `@`. `https://evil.com\@good.com/x` therefore yields
`host: 'good.com'` while every WHATWG client connects to `evil.com`. The doc
calls the parser "best-effort" but does not warn that `host` is unsafe for
security decisions.

**Relevant locations:**

- `src/urlparts.js:45-52` (authority extraction).
- `src/urlparts.js:81` (`lastIndexOf('@')`).
- `src/urlparts.md`.

**Verification steps:**

```sh
node -e "const u=require('./src/urlparts');
for (const s of ['https://evil.com\\\\@good.com/x','https://good.com\\\\evil.com/x'])
  console.log(u(s).host, '| WHATWG', new URL(s).host)"
```

Observed: `good.com | WHATWG evil.com` and `good.com\evil.com | WHATWG good.com`.

**Expected behavior:** Either the same host a client would connect to, or a
documented statement that `host` must not be used for security decisions.

**Actual behavior:** A host no HTTP client would connect to.

**Recommended remediation:**

1. End the authority at the first `/` or `\` (`resource.search(/[\/\\]/)`).
2. State in `urlparts.md` that the result is for display/tolerant parsing and
   must not drive allow-lists.
3. Add the two cases above to the test table.

### AUD-23 — `stream_xml_parse.guess` lets element names rewrite the emitted object's prototype

**Severity and impact:** Medium — correctness and security boundary. XML from
the outside world controls the shape and prototype of the objects the pipeline
emits. A child element named `__proto__` replaces the prototype and discards
its own value; `constructor`, `toString`, and similar names are merged with
inherited functions.

**Description:** `guess()` uses `child.name in out` on a plain object, so
inherited properties count as duplicates. `stream_xml_analyze` has the same
pattern with `analytics[path_str] ??= 0`, producing `NaN` for a root element
named `constructor`.

**Relevant locations:**

- `src/stream_xml_parse.js:102` (`in out`).
- `src/stream_xml_analyze.js:20`.

**Verification steps:**

```sh
node -e "const {Readable}=require('stream');const p=require('./src/stream_xml_parse');
Readable.from(['<root><item><__proto__>z</__proto__><a>1</a></item></root>'])
  .pipe(p(['root','item'],p.guess)).toArray()
  .then(r=>console.log(Object.getPrototypeOf(r[0])===Object.prototype, Object.keys(r[0])))"
```

Observed: `false [ 'a' ]`. With `<constructor>x</constructor>` the audit
observed `constructor: [ [Function: Object], 'x' ]`.

**Expected behavior:** Every element name is an own data property.

**Actual behavior:** Prototype swapped, values lost, inherited functions merged.

**Recommended remediation:**

1. Build `out` and `analytics` with `Object.create(null)` and use
   `Object.hasOwn`.
2. Add the reserved-name regression suite from AUD-12 to both helpers.

### AUD-24 — `escape_content_disposition` passes CR, control characters, and non-Latin-1 text through

**Severity and impact:** Medium — security and correctness. The helper feeds
`Content-Disposition` in `http_stream_range`. A bare `\r`, other C0 controls,
and any character above U+00FF are illegal in header values. Node's
`setHeader` rejects them, so every file with a non-ASCII basename (Cyrillic,
accented, CJK) is served as a 500 instead of a download; a framework without
Node's validation would emit an injectable header.

**Description:** Only `\`, `"`, `%`, `\n`, and `\0` are rewritten. There is no
RFC 5987 `filename*=` fallback.

**Relevant locations:**

- `src/escape_content_disposition.js:7-11`.
- `src/http_stream_range.js:33` (consumer).

**Verification steps:**

```sh
node -e "const e=require('./src/escape_content_disposition');const http=require('http');
for (const s of ['a\rb','a\x01b','файл.txt']) { try { http.validateHeaderValue('content-disposition','attachment; filename='+e(s)); console.log('valid') } catch (x) { console.log(x.code) } }"
```

Observed `ERR_INVALID_CHAR` three times.

**Expected behavior:** Output is always a valid header value, with a UTF-8
`filename*` parameter for non-ASCII names.

**Actual behavior:** Invalid characters emitted verbatim.

**Recommended remediation:**

1. Encode all `[\x00-\x1f\x7f]` the way `\n` is encoded.
2. Replace non-Latin-1 characters in the quoted fallback and add
   `filename*=UTF-8''<percent-encoded>` (as jshttp/content-disposition does).
3. Add tests for `\r`, `\x01`, and a non-ASCII name.

### AUD-25 — `fastdl` leaks its progress timer and throws a `TypeError` when the total size is unknown

**Severity and impact:** Medium — reliability. When the server ignores `Range`
and answers a chunked 200, `fastdl` rejects with
`Cannot read properties of null (reading 'toString')`, the 1-second status
interval is never cleared, `user_friendly_status` keeps firing forever, and the
process cannot exit.

**Description:** `setInterval(tick)` is created before the `try/finally` that
clears it, and `format_bytes(total)` throws when `total` is `null` before the
`try` is entered. The validation error `http_get_stream_range` attached to the
destroyed stream is never read either.

**Relevant locations:**

- `src/fastdl.js:65` (timer), `:71` (throw), `:73-84` (the `try/finally`
  that comes too late).

**Verification steps:**

1. Call `fastdl` with a `read_stream_with_range` stub whose `content_range` is
   `{first: 0, last: null, total: null}` (or a real server that ignores
   `Range`).
2. After the rejection, inspect `process.getActiveResourcesInfo()`.

The audit observed `['Timeout']` still active 2.5 s after rejection and two
additional `user_friendly_status` calls in that window.

**Expected behavior:** A `UserFriendlyError` such as "server did not return
the resource size" and no timers left behind.

**Actual behavior:** `TypeError`, leaked interval, spammed status callback.

**Recommended remediation:**

1. After obtaining `rs0`, reject early when `!Number.isInteger(total)` and
   destroy the stream.
2. Move `setInterval` inside the `try`.
3. Add a "server ignores Range" test.

### AUD-26 — `http_get_stream_range` accepts a chunked 200 for a suffix request and returns the whole body

**Severity and impact:** Medium — correctness. A caller asking for the last
99 bytes silently receives the entire resource. The doc promises that a server
ignoring the range is rejected.

**Description:** For the suffix form against a chunked 200, `content_range` is
`{first: 0, last: null, total: null}`. `actual_length = null - 0 + 1` is `1`
and `expected_length = Math.min(1, b)` is also `1`, so validation passes. The
same server with `Content-Length` is correctly rejected.

**Relevant locations:**

- `src/http_get_stream_range.js:46-49`.
- `src/http_get_stream_range.md:17-18`.

**Verification steps:** Serve a 1,000-byte body with `Transfer-Encoding:
chunked` and no range support; call
`http_get_stream_range(url, undefined, 99)` and count bytes read. The audit
observed `bytes received = 1000 (wanted 99)`.

**Expected behavior:** The stream is destroyed with a "range ignored" error.

**Actual behavior:** Full body returned with no error.

**Recommended remediation:** In the suffix branch, reject when
`out.content_range.last === null`; add the chunked-suffix test.

### AUD-27 — A valid-JSON non-object queue entry kills both Redis poll loops

**Severity and impact:** Medium — reliability. One poisoned sorted-set entry
whose text is `null` takes the worker down and every later message is left
unprocessed. The entry was already popped, so the producer never learns.

**Description:** The parse guard only catches `JSON.parse` failures. `null`
parses, `message.uid` throws inside the inner `try`, and the `catch` block
evaluates `message.uid` again while building the reject response, throwing out
of the loop.

**Relevant locations:**

- `src/redis_poll_zshift_callback_rpush.js:69` and `:92`.
- `src/redis_poll_zshift_spawn_rpush.js:78` and `:101`.

**Verification steps:** With `redis-v4` against the local Redis, `ZADD` the
string `null` (score 1) then a valid message (score 2) and start the callback
poller. The audit observed `poll loop DIED with TypeError: Cannot read
properties of null (reading 'uid') | remaining in input queue = 1 | messages
processed = 0`.

**Expected behavior:** The entry is logged under `log_waiter_error_parse` and
skipped.

**Actual behavior:** The poller rejects and stops.

**Recommended remediation:** After `JSON.parse`, `continue` when
`!message || typeof message !== 'object'` in both pollers, and add a test.

### AUD-28 — Unawaited `redis_rpush` in the spawn worker's status handler is an unhandled rejection

**Severity and impact:** Medium — reliability. If the push fails while the
child is running (dropped connection, closed client, `WRONGTYPE`), the
rejection is unhandled and Node's default policy terminates the worker mid-job.

**Description:** The fd-3 `stream_data_ln` handler calls `redis_rpush(...)`
without `await` or `.catch`. The line was rewritten in this range
(`rpush_p` to `redis_rpush`) but the fire-and-forget pattern was kept.

**Relevant locations:**

- `src/redis_poll_zshift_spawn_rpush.js:148`.

**Verification steps:** Run the spawn poller with a fake client whose `rPush`
rejects for the child's status line and a child that writes to fd 3. The audit
observed `UNHANDLED REJECTION ... redis connection lost`, exit code 4 under
`--unhandled-rejections=strict`.

**Expected behavior:** A status-push failure is logged or fails the job via
the surrounding promise.

**Actual behavior:** Unhandled rejection escapes an event handler.

**Recommended remediation:** `.catch(error => log(...))` on that call, or
capture it and reject the wrapping promise.

### AUD-29 — The watchdog dies on `SIGHUP`, orphaning its child and leaking the socket

**Severity and impact:** Medium — reliability. The supervised process keeps
running with no supervisor after a terminal or SSH session drops, defeating the
purpose of a watchdog. The `/dev/shm/watchdog-*.sock` file is left behind and
an orphan that keeps pinging it crashes on `ECONNREFUSED`.

**Description:** The child is spawned `detached`, so it does not receive
terminal signals; the watchdog forwards only `SIGTERM` and `SIGINT`.

**Relevant locations:**

- `src/cli-apps/watchdog.js:77` (`detached: true`).
- `src/cli-apps/watchdog.js:81-87` (signal handlers).

**Verification steps:**

```sh
node src/cli-apps/watchdog.js node ping.js & WP=$!; sleep 1
kill -HUP $WP; wait $WP; echo exit=$?; pgrep -af ping.js; ls /dev/shm/watchdog-*
```

The audit observed `exit=129`, the child still running with ppid 1, and one
socket file left in `/dev/shm`.

**Expected behavior:** `SIGHUP` treated like `SIGTERM`: child group
terminated, socket removed, exit 129.

**Actual behavior:** Watchdog dies, child orphaned, socket leaked.

**Recommended remediation:** Register `SIGHUP` (and `SIGQUIT`) handlers that
reject with the matching `ExitCodeError`; add a best-effort `process.on('exit')`
socket removal; add a test row for it.

### AUD-30 — Zombie grandchildren make `pgid_kill_grace` report "survived SIGKILL" and mask the real exit code

**Severity and impact:** Medium — reliability. In containers where PID 1 does
not reap (Node as PID 1 without `--init`), a child that spawned its own
children leaves zombies in the process group. The watchdog then waits the
full grace period, throws from its `finally`, and replaces the true reason
(heartbeat timeout 124 or the child's exit code) with exit 1 after an extra
5 seconds. The happy path exits 1 the same way.

**Description:** `kill(-pgid, 0)` succeeds while any member exists, including
`Z` state processes, so `pgid_exists` never turns false and `pid_exists` has
the same blind spot.

**Relevant locations:**

- `src/pgid_exists.js:6`.
- `src/pgid_kill_grace.js:12-33`.
- `src/cli-apps/watchdog.js:95-101`.

**Verification steps:**

```sh
WATCHDOG_INTERVAL=300 __TESTING__=1 node src/cli-apps/watchdog.js src/cli-apps/watchdog.d/spawn_children.js; echo exit=$?
```

The audit observed `[watchdog_end_error] ... Process group 3293 survived
SIGKILL` and `exit=1` after 5.8 s; `ps` showed two `[sleep] <defunct>` in the
group. `pid_kill_grace` on a zombie throws `survived SIGKILL` the same way.

**Expected behavior:** Zombies are not "alive"; the original error is
preserved.

**Actual behavior:** Extra delay, wrong exit code, misleading message.

**Recommended remediation:**

1. In `pid_exists`/`pgid_exists` (or the post-`SIGKILL` check) read
   `/proc/<pid>/stat` and ignore state `Z`.
2. Wrap the kill in the watchdog's `finally` so it cannot replace the primary
   error.
3. Implement the skipped "survived SIGKILL" test with a zombie
   (`sh -c 'sleep 0.1 & echo $!; exec sleep 100'`).

### AUD-31 — `shell_spawn().promise()` never settles when the child fills an unread pipe

**Severity and impact:** Medium — reliability and documentation. With the
default `stdio: 'pipe'`, a child that prints more than the pipe buffer
(about 64 KiB) blocks on `write` forever, and the promise never resolves. The
doc says output "is streamed (not buffered)" and that `promise()` resolves on
exit, with no warning that the caller must drain or ignore the pipes.

**Relevant locations:**

- `src/shell_spawn.js:45`.
- `src/shell_spawn.md:6` and `:24`.
- `src/shell_spawn.test.js` uses only `['true']`, which prints nothing.

**Verification steps:**

```js
await shell_spawn(['head', '-c', '200000', '/dev/zero']).promise().timeout(2000);
```

The audit observed `TimeoutError` with the child still blocked.

**Expected behavior:** Either a safe default (`['pipe', 'inherit', 'inherit']`)
or a loud doc note with a chatty-child test.

**Actual behavior:** Silent permanent hang.

**Recommended remediation:** Document the contract, consider inheriting or
ignoring stdout/stderr unless the caller passes `stdio`, and add a test with a
chatty child.

### AUD-32 — `shell` and `shell_json` always reject with `encoding: 'buffer'`

**Severity and impact:** Medium — correctness. Passing the documented
`execFile` option `encoding: 'buffer'` makes every successful command fail
with an empty `STDERR` message, because a zero-length `Buffer` is truthy.

**Relevant locations:**

- `src/shell.js:10`.
- `src/shell_json.js:10`.

```js
await shell(['true'], {encoding: 'buffer'});
```

Observed: `Process terminated with the following STDERR:\n\n`.

**Actual behavior:** Always rejects.

### AUD-33 — `make_progress` overestimates `rate` by counting the first sample's delta but not its time

**Severity and impact:** Medium — correctness. Two `add(10)` calls one second
apart report 20 units/s instead of 10, and `eta` is off by the same factor.
With 1-second ticks and the 10-second window it is a permanent ~10%
overestimate; early in a transfer it is about 2x.

**Description:** The window is `now - history[0].time`, but the summed delta
includes `history[0].delta`, which was accumulated before that timestamp.

**Relevant locations:**

- `src/make_progress.js:25` (history push).
- `src/make_progress.js:39-41` (rate computation).

**Verification steps:**

```js
const p = make_progress(100); p.add(10); await sleep(1000); p.add(10);
console.log(p.rate, p.eta);
```

Observed `20 4`; expected approximately `10 8`.

**Recommended remediation:** Sum `history.slice(1)` over
`now - history[0].time`, or keep `{time, done}` snapshots and compute
`(done_now - done_at_window_start) / dt`. Add a timing test.

### AUD-34 — `stream_strpbrk` and `stream_lines` corrupt multi-byte UTF-8 split across chunks

**Severity and impact:** Medium — correctness. Any non-ASCII text read through

straddling a chunk boundary and comes out as `��`. `stream_data_ln`,
`stream_xml_parse`, and `stream_xml_analyze` were already fixed for this with
`StringDecoder` and 1-byte-chunk tests; `stream_strpbrk`, and therefore
`stream_lines`, were not.

**Relevant locations:**

- `src/stream_strpbrk.js:12`.
- `src/stream_lines.js:8`.

**Verification steps:**

```js
const b = Buffer.from('café au lait\n');
await Readable.from([b.subarray(0, 4), b.subarray(4)]).pipe(stream_lines()).toArray();
```

Observed `[ 'caf�� au lait' ]`.

**Recommended remediation:** Use a per-instance `StringDecoder` as in
`stream_data_ln.js`; add the 1-byte-chunk test.

### AUD-35 — `stream_map_flatten` ignores backpressure

**Severity and impact:** Medium — reliability and memory. A generator that
yields many items per input (the natural use: expand one URL into all of its
pages) is drained to completion into the readable buffer regardless of how
slow the consumer is.

**Description:** `for await (const chunk of fn(item)) this.push(chunk)` never
checks `push()`'s return value.

**Relevant locations:**

- `src/stream_map_flatten.js:12-13`.

**Verification steps:** Pipe a generator yielding 100,000 items into a sink
with `highWaterMark: 1` that takes a tick per item; after 300 ms the audit
observed `readableLength` of 99,998 with a 16-object high-water mark.

**Recommended remediation:** When `push()` returns `false`, wait for `_read`
before pulling the next value, or document that the generator's whole output
per item is materialized.

### AUD-36 — `stream_xml_parse` retains ancestor text for the life of the stream

**Severity and impact:** Medium — performance. For a pretty-printed feed the
helper keeps two strings (indentation and newline) per record in the root
element's `text` and `raw` arrays for the entire document, which defeats the
purpose of a streaming parser on multi-GB inputs. Non-selected siblings are
retained the same way.

**Relevant locations:**

- `src/stream_xml_parse.js:23` (`elem.parent.raw.push(elem)`).
- `src/stream_xml_parse.js:39-42` (`ontext`).

### AUD-45 — Range parsing helpers accept syntactically invalid input

**Severity and impact:** Low — correctness and HTTP conformance.

- `http_stream_range` answers 416 to `bytes=5-3`. RFC 7233 §2.1 says a
  last-byte-pos below first-byte-pos is syntactically invalid and the whole

  error as unsatisfiable ranges. Locations: `src/http_range_parse.js:27`,

- `parse_http_content_range` accepts `bytes 500-499/1000` and
  `bytes 0-1000/1000`, both invalid per RFC 7233 §4.2, and throws a bare
  `TypeError` for non-string input. Location:
  `src/parse_http_content_range.js:6-16`.

**Recommended remediation:** Distinguish "cannot parse" from "unsatisfiable" in
`http_range_parse`; validate `total` as a non-negative integer; add the
